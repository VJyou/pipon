Flow 2 · Web3 · one-per-person mint

How Solana enforces "20+, one per person"

WALLET

1 · Open the gate

The gate account on Solana holds the rules: minimum age, prefectures, trusted CA keys, scope.

PHONE

2 · Bound to the wallet

The challenge is SHA-256(wallet address ‖ nonce), so the proof only works for this wallet.

CARD + PHONE

3 · Tap and prove

The card signs the challenge; the phone makes the same Groth16 proof as in Web2, with the gate's scope.

SOLANA · zk_gate

4 · Verify on-chain

Groth16 via alt_bn128 syscalls; CA, age, prefecture, date and the signer's wallet checked against the gate.

SOLANA · zk_gate

5 · Mint or reject

New nullifier → PDA created, Core NFT minted, same transaction (~144k CU). Nullifier exists → "Already claimed".

Public on-chain: the proof and its values — CA key hash, nullifier, date, age threshold, prefecture code.

Never on-chain: name, date of birth, address, ID image, My Number.

The nullifier is per card and per gate: another gate gets a different one, so wallets can't be linked across services.

And the Web3 flow. The user connects a wallet to a gate; the gate account on Solana holds the rules: minimum age, allowed prefectures, trusted CA keys and a scope. The request is bound to the wallet: the card signs a challenge made from the wallet address and a nonce, so the proof only works for that wallet. The phone makes the same Groth16 proof as before, with the gate's scope. Then one transaction: zk_gate verifies the proof with the alt_bn128 syscalls and checks the CA, age, prefecture, date and the signer against the gate. If the nullifier is new, it creates the nullifier account and mints a Metaplex Core NFT in the same transaction, about 144k compute units. If the nullifier already exists, the claim is rejected: one per person. On-chain you only find the proof and its public values; never a name, birthday, address or ID image.
